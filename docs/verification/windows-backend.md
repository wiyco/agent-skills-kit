# Windows backend implementation review

The maintainer explicitly requires successful Windows copying and native validation in ASK-012 (2026-10-16). This retains the issue's original acceptance criterion. ADR 0006's fail-closed gate remains in force while the backend is built; passing primitive tests alone must not enable or advertise the public installation path.

## Native primitives

The first implementation layer tested the real native primitives before exposing them to library operations. The second enables the read-only subset for Windows NTFS inventory; commit/cleanup primitives remain test-only until executor integration. Public Windows installation remains disabled until all layers are complete and natively verified.

- Root selection permits only fixed local drive prefixes. The drive root is opened with backup-directory/reparse-open flags; every subsequent root component is opened relative to its retained parent and rejects reparse points. Pure prefix checks reject UNC/device paths without network calls. Mapped/non-fixed drives are refused before opening the requested path. Caller-controlled ancestors remain required; Windows root ancestor aliases are explicitly unsupported.
- Descendants use a single validated UTF-16 component and `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory`, reparse-open behavior, an explicit file/directory type, synchronous I/O, and either open-existing or create-new disposition. There is no full-path descendant fallback, overwrite disposition or alternate stream syntax.
- Opened disk objects are checked through basic, standard, attribute-tag and 128-bit file-ID information. Every reparse tag/device, multiply-linked regular file, delete-pending object or invalid length is rejected. Native identity is not truncated to a 64-bit inode.
- Retained handles omit delete sharing, so ordinary pathname rename/deletion of those objects is denied while they are held. Read/write sharing is allowed; this does not freeze bytes, attributes or directory contents. Later inventory/verification must still compare bounded reads, digests and stamps. Kernel/user security privileges and hostile caller-root mutation remain outside the contract.
- Commit uses the held source object, a retained destination parent, a validated single component and `NtSetInformationFile(FileRenameInformation)` with replacement disabled. Its aligned variable-size SDK buffer is bounded by the component limit. There is no ordinary rename fallback, destination deletion or path-based merge.
- Cleanup uses `FileDispositionInfo` on an operation-owned handle, not a remembered pathname. This primitive does not establish ownership on behalf of its caller: the executor must supply only proven created objects and never reuse installed-payload handles as cleanup authority. Nonempty directory deletion fails.

Unsafe calls are confined to the native wrapper with live-handle, buffer-layout and ownership explanations at each boundary. The native tests establish component refusal/wide identity, exact byte I/O, create-new refusal, successful directory commit, last-moment file/empty-directory/symlink winners, reparse/hard-link rejection, parent rename denial while held and handle-based cleanup preserving an unrelated sentinel. They create only exclusive owned temporary roots and inert data. A missing Windows symlink privilege fails explicitly.

The initially evaluated `SetFileInformationByHandle(FileRenameInfo)` candidate returned Windows error 87 for an actual parent-relative directory rename in native CI (run 38913718515, job 117015834878). The implementation therefore selects documented user-mode `NtSetInformationFile(FileRenameInformation)` directly, preserving the parent handle and replacement-disabled flag. It never retries through a path-based rename. Native proof remains required before enabling the backend. This is a refinement of ADR 0006's proposed API direction, with unchanged containment/no-clobber requirements.

## Dependency review

`windows-sys` 0.61.2 is Microsoft's generated Windows SDK binding crate, MIT OR Apache-2.0, declared MSRV 1.71. Its sole dependency `windows-link` 0.2.1 has the same license and declared MSRV. Both already existed transitively in the committed lockfile; the direct Windows-only dependency adds the WDK/Win32 features needed for these APIs. No local tools or user-level configuration are installed or changed. Typed generated layouts and declarations avoid maintaining handwritten Windows ABI structs/link signatures.

Evidence: the exact cached registry package manifests and generated modules were inspected before use; [upstream Microsoft repository](https://github.com/microsoft/windows-rs) was checked live as nonarchived with activity on 2026-10-16. Its root GitHub license is not used to override the actual crate manifests' dual-license terms. Existing Cargo.lock records both exact versions/checksums. Rust 1.85.0 compatibility and native Windows Clippy/tests still require actual CI results, not the declared dependency MSRV alone. No dependency-advisory audit is claimed by this review.

## Read-only integration layer

Source inventory is implemented separately from public plan/apply support. It adds bounded directory enumeration through a retained-object cursor protected by an explicit per-handle scan mutex, local NTFS/remote-device checks and alternate data stream rejection. Full native stamps are retained for comparisons; ordinary portable mode intent is explicitly not ACL equivalence. See [validation](../validation.md#windows-read-only-inventory) for behavior, API considerations and tests. Windows copying remains required and gated.

The evaluated `ReOpenFile` directory-cursor candidate failed with access denied in Windows native CI (run 38917013663/job 117026966407). Enumeration instead uses the retained directory handle directly with a per-handle mutex and explicit restart. Every Arc clone shares the same lock; there is no global state, path fallback or new root lookup. Native repeated/concurrent scan tests and finite entry budgets gate this choice. The earlier candidate failure is not counted as passing evidence.

## Private creation descriptors (test-only integration boundary)

New staging/parent creation must apply a protected effective-user-only DACL in the native create operation; creating with inherited broad permissions and narrowing afterward is not acceptable. The candidate wrapper is exercised natively before enabling executor use. It obtains the thread token when impersonating, falls back to the process token only on `ERROR_NO_TOKEN`, requests query access, and never enables privileges or modifies a token. Anonymous/denied-token errors remain errors. Token-user storage is aligned and bounded; SID text comes only from the native conversion API. A self-relative SDDL descriptor sets the effective user as owner and grants only that SID inheritable file rights under a protected DACL. The SDK allocation is released with `LocalFree` after use.

The descriptor is supplied directly to `NtCreateFile`'s `OBJECT_ATTRIBUTES` while retaining the validated parent and exclusive `FILE_CREATE` disposition. There is no path-based create, ACL repair of an existing object, null DACL, source descriptor reuse or temporary permissive interval. This test-only boundary does not yet define final payload inheritance or enable Windows application.

Primary API sections reviewed 2026-10-16 UTC against windows-sys 0.61.2: [OpenThreadToken parameters/errors](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openthreadtoken), [GetTokenInformation buffers/TokenUser](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation), [SDDL descriptor components/protection](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-string-format), [ACE flags/file rights](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-strings), [descriptor conversion and LocalFree ownership](https://learn.microsoft.com/en-us/windows/win32/api/sddl/nf-sddl-convertstringsecuritydescriptortosecuritydescriptorw), and the previously reviewed NtCreateFile object-attributes contract. The existing windows-sys dependency enables its Threading feature; no version, lockfile package or local installation changes.

Reproduce on Windows with `cargo test -p agent-skills-kit --lib creation::tests --locked -- --nocapture`. Owned fixtures establish an actual inheritable Everyone read grant on a new parent, require its absence from the protected stage and inherited child, compare the exact stage DACL, and preserve the parent descriptor. A colliding existing file retains bytes and security. These are descriptor/creation tests; no second-user access attempt, impersonation/restricted-token scenario, source metadata copying, final destination inheritance, stage race/cleanup or interruption is claimed. Final native CI/Clippy/MSRV evidence is recorded separately on the PR.

## Destination inheritance candidate (test-only)

Windows does not assign a new default security descriptor during a rename. Additionally, ordinary traversal-bypass privileges mean a private wrapper DACL alone cannot protect a child with a broad DACL. Every staged object therefore inherits the effective-user-only staging DACL until commit. Payload owner/group use the current token's defaults; no source ownership or security descriptor is read for copying.

The candidate finalization runs **after** exclusive commit: `CreatePrivateObjectSecurityEx` derives file/directory inheritance from the real destination parent's bounded owner/group/DACL snapshot and query token using the file generic-rights mapping and `SEF_DACL_AUTO_INHERIT`. No creator/source descriptor, SACL or owner/privilege-check bypass flag is supplied. A null/absent resulting DACL is unsupported. `NtSetSecurityObject` on each retained committed object, with `WRITE_DAC`, installs its DACL and enables real destination inheritance. Each bounded inventoried entry is updated separately in parent-before-child order; no recursive user-space namespace propagation is delegated to an API. Existing selected parents are never modified. The inheritance descriptor uses `DestroyPrivateObjectSecurity`, distinct from the SDDL/SDK `LocalFree` allocations.

Permission propagation is **not atomic with directory commit**. Failure can leave a complete committed payload with restrictive or partially finalized destination permissions. Before enabling the executor, its typed outcomes/receipts must explicitly report that committed state and any finalization error; such failure must never authorize deleting the installed payload, rolling back earlier destinations, or claiming ordinary complete success. Process interruption between commit and finalization is also a required regression boundary. This candidate remains test-only pending those integration/reporting tests.

Primary references, reviewed 2026-10-16 UTC: [file security descriptors, rename and traversal rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [CreatePrivateObjectSecurityEx parameters/inheritance rules](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createprivateobjectsecurityex), [DestroyPrivateObjectSecurity ownership](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-destroyprivateobjectsecurity), and [automatic propagation of inheritable ACEs](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces). This API review is not itself evidence of native behavior.

Native reproduction: `cargo test -p agent-skills-kit --lib creation::tests --locked -- --nocapture`. New owned fixtures compare the committed root and descendant allow-grant policies against real native default creation under the same parent, including an inheritable Everyone-read grant and Creator Owner substitution, both with and without a duplicate inheritable user grant. They require private staging before/after rename, exact inert bytes and unchanged parent security. A real handle lacking `WRITE_DAC` must fail finalization while preserving the committed private directory. Windows directory rename refused an open descendant even with deletion sharing in native run 38930316438. Copy handles are therefore closed before exclusive commit. While every committed object is still private, permission handles are reacquired relative to the retained root, their full identities checked, and held without deletion sharing through all updates. The selected root remains held throughout. No test executes a payload or changes process privileges, real stores or user-level configuration. These tests do not establish second-user access, arbitrary enterprise ACLs, SACL/integrity propagation, interruption or successful public copy execution.

The inheritance fixture compares binary SID masks for current access and file/directory inheritance roles, combining duplicate allow grants and ignoring provenance-only INHERITED/auto-inheritance flags. It rejects every unknown ACE type/flag and does not implement a general ACL evaluator. Raw SDDL is not a permission-equivalence test: native creation and later inheritance may represent redundant owner grants differently. SDK SDDL string parsing stops at the first NUL within the reported allocation bound. The denied-WRITE_DAC fixture records its baseline after rename, keeping rename effects separate from finalization.

The initial `SetSecurityInfo` propagation candidate updated the root but left its child without the expected Everyone-read grant in native run 38929566111. That required test failed; implicit descendant propagation is not used. The replacement uses documented user-mode [NtSetSecurityObject parameters/rights/self-relative descriptors](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetsecurityobject), reviewed 2026-10-16 UTC, through the existing SDK binding. The positive fixture requires root-only updates to leave the retained child private, then finalizes that exact held child and compares both resulting grant policies with native creation. Win32 `SetKernelObjectSecurity` was not selected: its documentation advises against filesystem use. Finalization is still a test-only candidate pending native proof and executor integration.

A late, actual directory reparse point is inserted into the committed fixture before finalization. Only the known retained root/file handles are updated; outside owner/group/DACL bytes and sentinel content must remain unchanged. This models an unexpected post-commit entry and does not permit reparse inputs. Missing link privileges fail explicitly. The SDK inheritance-allocation destructor receives an address of uniquely mutable pointer storage, consistent with the documented in/out lifetime despite the generated const-pointer parameter.

## Copy backend candidate

The next implementation layer adds a test-only Windows executor under the library. Public `apply_plan` remains unsupported on Windows until final native acceptance coverage and review are complete. It consumes the same immutable plan, whole-plan verification, copy budget and report types as Unix; the CLI owns no second engine or path registry.

The candidate exclusively creates protected private parents/stage/payload entries through retained NTFS handles. Source components are reopened no-follow and compared with approved full snapshots, bounded original bytes/digests are copied and read back, source read-only intent is applied to owned outputs, and exact stage entry sets/stamps/security are checked. Descendant handles close before native no-replace commit. All permission handles are then reacquired while the committed tree is private, checked against recorded full identities/security and retained through explicit parent-before-child finalization. A finalization error is a committed permission failure; it never authorizes rollback/deleting the payload. Created parent directories are reused only with operation ownership and remain with diagnostics when unused.

Pre-commit cleanup reacquires only recorded entries from the held private stage, verifies every identity/security descriptor before mutation, clears owned read-only intent as needed and deletes exact held objects in reverse order. Foreign/replaced/unknown entries stop cleanup rather than gaining prefix-based deletion authority. A native create followed by failed identification has an explicit unconfirmed-creation error/remnant diagnostic. Source ownership, security descriptors, named streams, extended attributes and executable instructions are never copied/executed.

Initial candidate reproduction on Windows: `cargo test -p agent-skills-kit --lib windows_candidate --locked -- --nocapture`. Owned fixtures exercise original manifests/resources/empty directories, three core user/project placements and alias deduplication, Unicode/spaces/unpaired UTF-16 names, inert executable-looking content, unchanged repeats, DOS read-only intent, an injected post-commit permission error with compatible receipt projection, and an injected write failure preserving an unrelated prefix-matching directory. These tests are not yet native passing evidence until final CI and QA are recorded. Actual permission denial, concurrent races, source/stage swaps, cleanup uncertainty and process termination still require integration evidence before enabling public copying or closing ASK-012. Injected codes are not actual disk exhaustion or a kernel permission-denial experiment.

Native run 38939388788 exposed a same-length staged byte mutation that passed metadata-only pre-commit checks. The executor therefore retains the original approved digest and performs another bounded byte readback immediately before commit, with before/after identity/metadata/security checks. The implementation PR carries its own regression that changes bytes while preserving length and restoring observed write/change epochs; it must fail before commit and remove only owned staging. Stage directory membership verification indexes children once instead of rescanning every record per directory. These fixes do not relax the private-staging/ancestor trust assumptions or promise a mutable-filesystem snapshot.
## Copy boundary regression layer

The Windows candidate's dependent boundary tests exercise actual NTFS permission denial by denying only `FILE_ADD_SUBDIRECTORY` on an owned readable target parent. Planning/preflight still succeed; a prior target remains installed, the denied target fails with native permission denied, and the next target is not attempted or succeeds according to `stop_on_failure`. Existing parent DACLs remain unchanged. A distinct source-only Everyone-read grant must not appear on the copied file; later manual edits make the preview conflict and remain untouched.

Deterministic pre-commit hooks introduce competing files, empty directories and real directory reparse points after validation; native commit must preserve each winner and outside sentinel. Source byte/reparse swaps and staged byte/entry-set changes must fail before commit. Cleanup must preserve an unrecorded foreign staged entry and report its retained directory. Two actual worker threads rendezvous at native commit using bounded readiness/release channels; both are released/joined before assertions, with exactly one successful commit and no prefix-based deletion.

Reproduce with `cargo test -p agent-skills-kit --lib windows_candidate --locked -- --nocapture` on Windows. These are candidate regressions awaiting final native CI, not proof of public enablement or process-interruption recovery. Symlink privilege failure is an explicit failed prerequisite. Only original owned temporary fixtures and the trusted test executable are used; no real skill store, global environment mutation or payload execution occurs.
