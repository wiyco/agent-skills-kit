# Opt-in core-host discovery smoke tests

Refs #22 (ASK-022). These procedures test metadata discovery, not skill invocation, model behavior or universal host support. They are outside required PR CI. The original fixture is [`ask-discovery-probe`](../../fixtures/discovery/ask-discovery-probe/SKILL.md); it contains only SKILL.md and requests no actions. Never invoke it, a bundled skill, a model turn, shell interpolation from skill content, hooks or downloaded code.

## Isolation and approval boundary

Use existing trusted host binaries only. Do not download/update hosts, sign in, supply credentials, accept new service agreements, connect to an existing daemon or enable paid providers. If any is needed, stop and record the limitation. Do not use real skill stores or copy real configuration/credentials into a fixture. Windows/Linux procedures require a separately verified disposable OS account/container or comparable isolation; none is claimed validated here.

The macOS helper creates and removes only its own `/private/tmp/ask-host-smoke-*` and guard directories. It constructs a fresh **child-only** environment, without inherited credentials, with temporary HOME, CODEX_HOME, XDG locations and TMPDIR. It does not change the parent environment or global configuration. The OS profile denies network, real-home reads, keychain service lookups and outside writes (except `/dev/null`). Before any host launch, a trusted Python subprocess must demonstrate denied real-home metadata access, an unchanged outside-owned sentinel after denied write, and denied loopback connection. No fallback drops these restrictions. This is evidence for this exact macOS setup, not a portable security sandbox or proof against malicious host binaries.

Host/system configuration outside the real home may differ on other machines. Inspect managed configuration before testing; stop if it can introduce plugins, hooks, auth helpers or remote catalogs. Local and system behavior must never be inferred from metadata listing alone. Bundled Codex system skills may be materialized inside the temporary CODEX_HOME; they are not invoked or reported as this fixture.

## Codex: executable procedure

Host-owned sources reviewed 2026-10-16: [Build skills, Where Codex loads local skills](https://learn.chatgpt.com/docs/build-skills), [App Server, Initialization and Skills](https://learn.chatgpt.com/docs/app-server), and [Environment variables, Core locations](https://learn.chatgpt.com/docs/config-file/environment-variables). The historical `developers.openai.com/codex/skills/` and `/app-server/` links redirect to these pages. CODEX_HOME isolates state; it does **not** replace the user authoring root under temporary HOME.

Build the existing workspace CLI, then pass absolute paths to the installed trusted Codex and that CLI. Example for this verification machine (adjust binary paths only after reviewing their identity):

```sh
cargo build --workspace --locked
python3 -B .github/scripts/smoke_codex.py --codex /opt/homebrew/bin/codex --installer "$PWD/target/debug/agent-skills-kit" --scope project
python3 -B .github/scripts/smoke_codex.py --codex /opt/homebrew/bin/codex --installer "$PWD/target/debug/agent-skills-kit" --scope user
```

For each scope the helper uses separate fresh state, checks an empty discovery baseline, copies the trusted installer executable into owned state, and runs its library-backed `install --target codex --yes` with explicit temporary roots. No installation engine is duplicated in the helper. It then starts a new stdio app-server and sends only `initialize`, `initialized`, and `skills/list` with the explicit project cwd and forceReload. It requires exactly the fixture's expected native path/scope, enabled metadata, no host discovery errors and unchanged original/installed bytes. No `thread/start`, `turn/start`, login or provider request is sent. Replies are bounded to 2 MiB and 20 seconds per response; processes are reaped before temporary cleanup. A failure exits nonzero and never prints a passing result. Sanitized success JSON contains no actual home or temporary basename.

An absent baseline followed by metadata listing demonstrates discovery of this installed fixture only. It does not establish ancestor traversal, collision precedence, invocation, all resource formats, alternate profiles, IDE/cloud variants or other OS/host versions.
