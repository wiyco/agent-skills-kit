# Windows permanent-removal backend review

Status: experimental implementation for #113. Final revision, native CI results and remaining limitations are recorded in the separate QA Evidence comment on PR #121. Local macOS compilation/tests do not compile or validate the Windows backend; merge and alpha require satisfactory final native evidence.

## Authority and primitive changes

The public library accepts only a consumed `ApprovedRemoval` from a complete current selection/preview. Common preflight rechecks protected context/container roots, known/unknown reader impact and complete inventory. A receipt, remembered path or generic copy approval grants no deletion authority. Native eligibility remains the existing fixed local NTFS/no-reparse/no-unsafe-stream policy; no UNC/remote/new filesystem or OS validation claim is added.

Reuse the existing retained-parent `NtCreateFile` component walker with one explicit new access/sharing profile: existing-object `FILE_GENERIC_READ | DELETE`, `FILE_OPEN`, only `FILE_SHARE_READ`, and the existing no-reparse/type flags. Do not request attribute-write rights, clear readonly attributes, change source DACLs or close another process's handles. Conflicting read/delete/write handles can refuse opening; they are not bypassed. Existing inventory/copy/permission/cleanup callers keep their exact prior sharing masks. The raw file-disposition primitive is renamed `dispose_verified` to distinguish its neutral native action from the caller's separately proven owned-cleanup or current-plan authority; its FFI behavior is unchanged.

Open/recheck the selected root's full native identity and exact spelling, inspect its complete payload through that held object, then exclusively create a protected enclosure using the previously reviewed effective-user creation descriptor. Detach the verified DELETE-capable object with the existing parent-relative `NtSetInformationFile(FileRenameInformation)` replacement-disabled primitive. This targets the held object rather than a Unix source-name check/rename pair. No ordinary move/delete fallback or receipt ownership inference occurs.

Verify the complete detached inventory, allowing only the expected root change-time delta from rename. Acquire retained read/DELETE handles for every approved directory/file; compare exact preconditions before any disposition. A final complete bounded directory-name audit detects extra/missing/spelling changes before the first permanent call. Approved handles disallow new write/delete opens, while actual sharing behavior still needs native tests. Directory timestamps after this operation's own child removals are not treated as an atomic NTFS snapshot: retained identity/kind/readonly intent, security descriptors, bindings and empty-directory checks remain gates. Each file's full stamp, security descriptor, length and digest are rechecked immediately before disposition.

Dispose deepest first, close this operation's relevant handles, then check the old binding. Sharing/delete-pending or otherwise unconfirmed absence is explicit failure/unknown state, never automatic success or force. An unrelated new occupant is not deleted. Every directory must be empty; the root and private enclosure are last. The mutex-wrapped directory reader gains a consuming `into_file` solely to make handle closure explicit; no unsafe binding is added. Graph ownership releases descendant handles before any no-replace restoration, and releases directory references before claiming successful deletion.

If no permanent call was attempted, a refused/stale detached object can be restored with native no-replace rename, preserving a concurrent original-name occupant. After an irreversible attempt, retain partial state with complete removed/remaining/not-attempted/unknown outcomes and uncertainty rather than reconstructing an incomplete tree. Private enclosure names remain diagnostics, not future cleanup authority. Enclosure cleanup refuses and reports unexpected siblings. Unknown-entry observations are bounded and may be explicitly incomplete.

## Required native scenarios

The Windows unit matrix uses original owned NTFS fixtures and inert bytes only: actual successful removal/no stage remnants; stale bytes/hard links/alternate streams; cloned discovery-handle refusal; source directory and actual reparse substitutions before DELETE-open; held-root external rename refusal; edited detached data restoration; concurrent original-name occupants; native no-replace collision; actual parent-DACL create denial; readonly refusal without attribute repair; controlled post-removal partial failure; a live share-delete read lease and honest pending/absence handling; stage pinning; new writer refusal; unexpected enclosure siblings; two native removers contending for one DELETE capability; and real process kills before detach, after detach and after the first confirmed removal.

ACL fixture functions are moved unchanged from the existing copy tests to a Windows test-only support module, so tests share reviewed SDK glue instead of adding another unsafe implementation. Only the original fixture owner restores fixture attributes/ACLs for teardown after assertions. Production never performs that repair, tests never touch real skill directories or credentials, and skill content is never executed. The interrupted-child helper is inert unless its explicit owned-fixture parent supplies the validated temporary root/marker.

## Primary documentation reviewed 2026-10-17

- [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile): DesiredAccess, RootDirectory, ShareAccess, FILE_OPEN/FILE_CREATE and reparse options. The documented user-mode equivalent links to [ZwCreateFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwcreatefile), whose sharing remarks explain compatibility with existing opens. These are access/containment design sources, not runtime proof.
- [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew): delete/share compatibility and readonly behavior; this implementation still uses the reviewed native relative walker, not a full-path ancestor shortcut.
- [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) and [FILE_DISPOSITION_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_disposition_info): exact existing SDK class/structure and required access. No POSIX-delete/ignore-readonly extension is enabled.
- [DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew), Remarks: open-handle and pending-deletion lifetime distinctions inform the negative live-lease test. This is not the mutation API used here and does not prove every NTFS/host behaves identically.
- [Existing Windows backend review](windows-backend.md): previously reviewed native rename, local-volume gate, private creation descriptors and unsafe boundary sources. The new removal operation needs its own final native evidence; successful copying alone is insufficient.

Caller-controlled roots/ancestors and stopped skill writers remain required under ADR 0009. Privileged/hostile same-identity staging mutation, arbitrary mutable-tree snapshots, mapped-file behavior, malicious filesystems, topology/privilege changes, crash durability, secure erasure and undo are not promised. Real Windows terminal/ConPTY/Windows 11/ARM deployments are not validated by compilation or Server/x64 tests.
