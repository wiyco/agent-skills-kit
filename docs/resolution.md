# Explicit-context path resolution

`resolver::resolve` takes a validated `Catalog`, target ID/alias, scope, and `InstallContext`. The context contains a requested native platform, optional user/project/application-workspace roots, and an explicit `OsString` override map. It never discovers HOME/CWD/Git roots, reads process variables, calls a generic OS-directory helper, changes environment/CWD, probes paths, canonicalizes roots, or creates directories. Roots and destinations need not exist.

Only a documented scope enabled for the requested native platform can resolve. Unknown IDs, absent scopes, excluded/foreign platforms, unverified/unsupported/import-only statuses, configuration-required states, and missing write paths are typed errors. Configuration-required adapters stay blocked until separate configuration verification enables their rules; `--yes` is not an override. Bundled candidates remain unverified until ASK-006 adds the evidence-backed adapter tests. Schema tests do not authorize them automatically.

## Root and override semantics

All supplied path bases must be absolute native paths. Empty values, NUL, parent traversal and invalid native components are rejected. Relative values are never interpreted against process CWD, a different scope, or a presumed home. No tilde, shell, `$VAR` or textual template expansion occurs. Ordinary current-directory components may be interpreted by Rust's native path representation; parent components are rejected rather than lexically normalized across possible links.

Only a rule with `PathBase::Environment` uses its exact documented variable name. Keys are logical, case-sensitive catalog identifiers even on Windows; callers supplying process values should query the documented key explicitly. Unknown override keys have no effect. A present empty/relative override is an error even if a fallback exists. Only an absent override can use its separately modeled fallback; absent fallback/context is an error. A literal home-based rule stays home-based even if the caller supplies an unrelated XDG variable. Do not infer an XDG or host-specific rule from a path's resemblance to an OS convention.

Roots and values use `PathBuf`/`OsString`; no UTF-8 conversion is needed to resolve them. Native Unix non-UTF-8 bytes and Windows wide values retain identity. Structured results contain native paths; a future JSON/terminal renderer must encode/escape them explicitly rather than assuming serde/string display is lossless or safe for terminals.

The requested platform must match the compilation target. Windows drive/UNC paths are interpreted only on native Windows. Fully qualified disk and UNC paths and reviewed verbatim disk/UNC prefixes can be represented; drive-relative (`C:folder`), drive-root-relative (`\folder`), device and opaque verbatim namespaces are rejected. Invalid Windows characters, trailing dot/space and documented device names (including extensions and COM/LPT superscript forms) are rejected in normal components. Device-basename padding is conservatively rejected too. Accepting a lexical UNC path does not assert network-filesystem installation support. Missing OS/filesystem/backend capabilities remain later execution failures under the threat model.

## Results and safety boundaries

The result names the canonical target, scope/platform, preferred skills-container root, known discovery descriptors, selected context/override/fallback provenance, unchanged source evidence, and deterministic deduplicated warnings. A validated skill name is appended by later planning. Native placement is not silently consolidated with compatibility readers. Ancestor discovery is described, not expanded by filesystem scanning. Missing context for a described read rule fails explicitly rather than inventing a location.

Warnings disclose nonexclusive placement, missing host/resolver evidence, unexpanded ancestor discovery, and metadata limitations. Path computation does not establish actual directory identity, permissions, containment, existence, host discovery or copy safety. Planning/execution must implement the [accepted threat model](threat-model.md), including explicit root trust/canonicalization, descendant no-follow behavior, stale preconditions, overlap and exclusive commit. A successful resolver call is not a supported installation claim.

## Verification and sources

Resolver tests use original synthetic rules and caller-created temporary roots, with no real agent stores or untrusted skill execution. They cover all context bases, missing/nonexistent roots, spaces/Unicode, explicit overrides/fallbacks, ignored unrelated OS variables, disabled statuses, alias/provenance/discovery/warnings, malformed paths, and native encoding. A self-test subprocess runs under a nested test-owned CWD with an explicit worktree root; only child-scoped test input is supplied, without changing the parent CWD or global HOME/environment. Windows-only tests exercise native drive/UNC/device/reserved-name behavior; Unix encoding tests are separately gated. Native CI is required before claiming those platform cases passed.

Microsoft documentation is OS syntax evidence, not authority for a host's skill path. Host-specific override rules still require host-owned sources; this generic interpreter adds none to bundled candidates.
