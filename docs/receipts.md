# Observational receipt schema

The receipt API provides a pure, bounded codec and `Receipt::from_report(plan, &report, operation_id, limits)` for an actual executor attempt. `Receipt::new(document, limits)` validates structural relationships; `from_json` and `to_json` read/write caller-owned byte buffers. No receipt API inspects, copies, chmods, deletes or persists filesystem content.

Schema version 1 records a caller-selected `operation_id`, native platform, explicit scope, `blake3_256` digest interpretation, deduplicated source payload records, target selection labels, destination outcomes and optional preflight/cleanup diagnostics. Each requested source/target pair must appear exactly once across destination attributions. Each destination also records its original create/unchanged/conflict/unsupported preview and all known blockers, so a preflight-blocked unmanaged conflict remains clear even when every actual outcome is NotAttempted. Preview classifications must agree with actual outcomes. Created, Unchanged, Failed and NotAttempted are distinct. Failed requires a diagnostic; attempted results require a path, and repeated exact attempted path labels are rejected. A preflight failure cannot coexist with attempted outcomes or cleanup activity. Unresolved NotAttempted requests may retain the same unverified path label.

An operation ID is a 1–128 byte ASCII letters/digits/dot/underscore/hyphen correlation label chosen by the caller. The library does not generate IDs, guarantee uniqueness or infer ownership from them. Digests use exactly 64 lowercase hexadecimal characters; directories have neither file bytes nor a digest. Source root/entry modes record only intended ordinary bits capped at 0755. Source content digests are integrity observations, not malware review or proof of current bytes.

## Lossless native paths

Paths are tagged data, for example `{"format":"unix_utf8","data":"/fixture/sample"}`. Valid Unicode paths use `unix_utf8` or `windows_utf8` text. Non-Unicode paths use `unix_bytes` (native byte integers) or `windows_wide` (u16 integers, preserving unpaired surrogates). Byte/wide forms must actually contain non-Unicode data, avoiding multiple encodings of the same spelling. No normalization or lossy replacement occurs. Empty/NUL paths and unsafe relative entry traversal are rejected.

Imported foreign-platform paths remain readable as data. `NativePath::to_native` refuses the wrong native family instead of interpreting Windows labels as Unix paths or vice versa. Windows codec tests exercise actual Windows native string APIs; this is independent of native Windows copy verification. Parsing validates data shape, references and resource bounds, not actual filesystem layout, host support, permissions, current identity or digest truth. A structurally valid forged/stale Created receipt is still untrusted data and cannot authorize replacement, deletion or adoption. Unchanged explicitly records preexisting content with no creation claim.

## Bounds and compatibility

`ReceiptLimits` defaults/ceilings: JSON 2/16 MiB; payload entries 65536/65536; one path 32768/32768 native units (Unix bytes or Windows u16); aggregate paths 16/64 Mi units; combined preview/outcome/preflight/cleanup diagnostics 4096/131072. Limits are positive. Fixed structural ceilings are 128 sources, 256 targets and 1024 source/target combinations/destination rows. Target labels are at most 4096 UTF-8 bytes so unresolved selection text can be recorded; operation labels are at most 256 bytes. Individual recorded file lengths cannot exceed the inventory reader's 256 MiB ceiling. Oversized receipt output fails in a bounded writer before returning bytes, not after unbounded serialization.

Unknown versions, fields, enum values, duplicate fields, malformed/corrupt JSON, invalid digests/modes, missing manifests, duplicate source/entry/reference records and inconsistent outcomes fail explicitly. Unknown versions are detected before interpreting a future document layout. JSON errors retain line/column without echoing attacker-controlled fields into a diagnostic. The immutable `Receipt` wraps validated data; a public `ReceiptDocument` is only model input until validated. Version 1 is a strict observational format, not an authentication or ownership protocol.

Only the existing serde/serde_json dependencies are used. Tests use original synthetic path labels without opening them, exercise exact byte/structural boundaries and corrupted data, preserve Unix non-UTF-8 and Windows unpaired-surrogate identity on native runners, and round-trip foreign records as inert data. No real skill stores, process environment changes, telemetry, new installation paths or tool installations are involved.

## Persistence and recovery boundary

Callers may explicitly store encoded bytes in their chosen location **outside skill payloads**. There is no hidden home state or automatic receipt discovery. A stale receipt does not bypass a fresh plan or its execution checks. Cleanup authority remains with live operation-owned handles under [execution.md](execution.md); an ID, recorded path, staging prefix or parsed receipt cannot recreate it.

Receipt construction borrows the full `InstallReport`, checks its exact native labels/attribution against the supplied plan, and preserves preview blockers and actual outcome distinctions. It bounds paths, entries and diagnostics while constructing records. It does not authenticate a caller-mutated report or claim that files are still unchanged. The report remains available if conversion, JSON encoding or the caller's storage write fails; a successful installation must not be reported as absent or rolled back because receipt storage failed. The receipt keeps stable coarse diagnostic classes, operation/constraint labels and native error numbers; the live plan/report retain full typed causes.

## Reruns and recovery

1. Keep the actual report and, when wanted, explicitly encode/store the receipt outside payloads. Store it appropriately for sensitive absolute path labels; the library adds no telemetry or logging service.
2. Retry by validating the currently selected source and building a **fresh plan**. Earlier successful identical destinations become Unchanged; different/manual content remains Conflict. A stored Created result is historical data, never overwrite permission or evidence of current ownership.
3. Preserve all per-destination outcomes: Created, Unchanged, Failed and NotAttempted. A later failure does not remove an earlier success; explicitly continuing independent destinations can produce another later success. Native competing commits allow one winner, and a subsequent fresh plan may recognize its bytes as preexisting identical content without claiming them as this attempt's creation.
4. For CreatedParentRetained, StageChanged or cleanup I/O diagnostics, leave uncertain remnants alone. Inspect only locations authorized by the caller. Prefixes/receipt IDs cannot establish ownership, and no automatic orphan deletion API exists. Any consequential manual cleanup needs the maintainer's explicit decision after ownership review. Unknown extra data must remain untouched.
5. Reject malformed/unknown-version receipts rather than repairing them into authority. A killed process may leave staging or a complete destination without any report/receipt; absence of a receipt is not permission to reinstall, replace or delete. This is not a cross-target rollback or power-loss recovery protocol.

Native tests persist a caller-selected receipt outside all skill payloads, verify unchanged reruns and preexisting unmanaged content without inode replacement, reject mismatched report labels, keep reports after receipt budget/encoding failure, and preserve manual edits after stale/corrupt receipt reads. Existing deterministic executor hooks exercise partial batches, retries that preserve earlier success, cleanup substitution and retained-parent diagnostics with receipt round trips. No recovery code deletes from parsed paths. Windows tests validate the native path codec and actual candidate committed-permission receipt projection; native copy evidence is recorded separately in [the backend review](verification/windows-backend.md).
