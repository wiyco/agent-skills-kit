# Catalog schema and bundled evidence

The library's `catalog` module validates versioned target metadata without reading the filesystem, process environment, or network. `Catalog::from_json` parses bounded JSON; `Catalog::new` validates caller-created data; `Catalog::bundled` loads versioned core documentation candidates. Iteration is deterministic. Unknown IDs, fields, enum values and schema versions do not become defaults.

Every definition names a product variant, aliases, scopes and platform candidates. A scope's preferred write path is separate from host-readable discovery paths. A missing write path is unavailable, not a request to guess. Paths use typed context/environment bases and literal components; environment fallbacks are explicit. Application workspace and project context are different bases. See [ADR 0007](adr/0007-catalog-schema-versioning.md) for identity and compatibility policy.

## Current evidence and limitations

Reviewed on 2026-10-16. These are rolling host documentation observations, not pinned host-version or native discovery results. All three core CLI project/user scopes are `Documented` with native lexical resolver tests; this is bounded placement support with the limitations below. No actual host discovery has been run. Evidence records keep those dimensions separate, with adapter resolver IDs separate from empty real-host discovery lists.

| CLI variant | Preferred project / user root in reviewed documentation | Additional discovery / evidence |
| --- | --- | --- |
| Codex (`codex`, alias `codex-cli`) | `.agents/skills` / `$HOME/.agents/skills` | Repository ancestor scanning is described in **Where Codex loads local skills**. [Original URL](https://developers.openai.com/codex/skills/) redirects to [the reviewed canonical page](https://learn.chatgpt.com/docs/build-skills). |
| Claude Code (`claude-code`) | `.claude/skills` / `~/.claude/skills` | **Choose where skills load** also describes other scopes and nested/additional-directory behavior, which are not enabled here. [Official documentation](https://code.claude.com/docs/en/skills). |
| OpenCode (`opencode`) | `.opencode/skills` / `~/.config/opencode/skills` | **Place files** and **Understand discovery** describe Claude/agent-compatible read locations as well as native placement. Preferred writes remain native. [Official documentation](https://opencode.ai/docs/skills/). |

The documentation does not establish a tested version or every native OS combination. Platform arrays identify native lexical resolution candidates, not host discovery or safe installation claims. Admin/system/plugin/cloud stores are outside the modeled write scopes. Selecting a host does not imply exclusive visibility. Host-supported links do not override this project's stricter copy-only/no-descendant-link policy.

The reviewed [OpenCode skills](https://opencode.ai/docs/skills/) and [configuration](https://opencode.ai/docs/config/) pages did not establish an `XDG_CONFIG_HOME` skills override during this review. The bundled rule therefore records only the documented literal home-relative root; it does not silently infer an XDG rule. Schema validity is not permission to infer additional override paths.

## Context examples

Original `tests/fixtures/catalog-contexts.json` demonstrates an XDG-shaped environment base with an explicit home-relative fallback and a separate application-workspace base. These two synthetic definitions are unverified, have no host-owned evidence, and are excluded from `Catalog::bundled`. They demonstrate schema expressiveness without inventing an installation path for a real host. The examples are inert metadata, not Agent Skills content.

Schema tests validate duplicate ID/alias/variant rejection, unknown scope/version/field handling, unsafe components, environment names and fallbacks, scope consistency, evidence gaps/dates, statuses, parser limits and serialization. Bundled-example tests check deterministic metadata, native versus compatibility placements, explicit unknown support, and empty real-host test evidence. None of these exercises a host or an installation engine; ASK-005/006 and subsequent safety work provide those separate layers.

## Codex CLI adapter review

`core_targets::codex_explicit_scopes_and_alias` and `core_targets::codex_context_and_variant_boundaries` test project/user placement, the canonical alias, explicit missing context, ancestor descriptors, shared-reader warnings, and rejection of unmodeled variants. These run with native paths on the required Linux/macOS/Windows CI matrix; they do not run Codex or prove skill discovery. The source does not establish a minimum CLI version or OS-specific discovery guarantees. No IDE/cloud/admin/system variant is enabled by analogy. No host-specific reserved local skill name is established by the reviewed page; general skill validation remains separate work.

The [environment variable reference, Core locations](https://learn.chatgpt.com/docs/config-file/environment-variables) describes `CODEX_HOME` as state storage including skills. [Advanced configuration, Config and state locations](https://learn.chatgpt.com/docs/config-file/config-advanced) describes that state root but does not establish a replacement for the explicit `$HOME/.agents/skills` authoring root in **Where Codex loads local skills**. All three pages were reviewed on 2026-10-16, against rolling documentation with no pinned host version. This adapter follows the explicit authoring table and does not interpret `CODEX_HOME` as a write override; alternate/legacy state skill locations remain unverified. This limitation is returned in resolution warnings. It must be revisited before claiming configuration-complete or version-specific host coverage.

Codex documents keeping duplicate skill names separate and following skill-folder symlinks. This library's stricter no-descendant-link copy policy still applies. Codex placement can also be visible to OpenCode according to its independently reviewed compatibility discovery table. The pure resolver does not enumerate ancestors or inspect host enable/disable configuration.

## Claude Code CLI adapter review

Reviewed on 2026-10-16 against rolling documentation. [Explore the .claude directory, Introduction and File reference](https://code.claude.com/docs/en/claude-directory) explicitly establishes project `.claude/skills`, user `~/.claude/skills`, the `CLAUDE_CONFIG_DIR` replacement for user paths, and Windows `%USERPROFILE%` home interpretation. The caller supplies that home; the library does not read USERPROFILE. The user rule uses the exact override, falling back only when absent. Empty/relative override values are rejected by installer policy, not claimed as a reproduction of all host configuration behavior. Project placement is independent of the user override.

[Skills, Choose where skills load; Load skills in monorepos and subdirectories](https://code.claude.com/docs/en/skills) establishes ancestor discovery. Version-specific `/cd` behavior (2.1.246+) and main-checkout fallback for worktrees (2.1.277+) are outside this explicit-root resolver. Neither the minimum version for ordinary roots nor actual discovery on all operating systems was tested. Nested/additional directory loading is not enumerated. The same page's **Resolve skills that share a name** establishes enterprise > personal > project precedence; a successful copy does not prove which command is active. Its link support does not relax this installer's stricter policy.

The **Choose where skills load** and **Names reserved for synced skills** sections reserve local folder `synced` in every capitalization and `anthropic-skills` plus its colon namespace. `TargetDefinition::reserved_skill_name` exposes these core CLI policies without changing the JSON schema or public record layout. Callers must check folder and frontmatter names before planning; `None` is not general syntax validation. The documented case-insensitive rule is applied to `synced`; the namespace rule follows the documented literal spelling. General syntax, character restrictions and filesystem safety remain the validator's responsibility. No reservation is inferred for custom products or plugin variants.

`core_targets::claude_scopes_and_config_override`, `claude_missing_and_invalid_context`, and `claude_reserved_names` cover both scopes, ancestor metadata, default/override provenance, missing/invalid inputs, override independence, reserved-name boundaries and unsupported variants on native CI. These tests perform no writes or host invocations. Real-host discovery evidence remains empty. OpenCode's documented `.claude` reader is disclosed; that does not imply it follows arbitrary alternate Claude configuration roots. Desktop/Cowork, cloud, enterprise and account/plugin-managed stores remain outside the enabled variant.

## OpenCode CLI adapter review

Reviewed 2026-10-16 against [Agent Skills, Place files; Understand discovery](https://opencode.ai/docs/skills/). Native preferred writes remain project `.opencode/skills` and user `~/.config/opencode/skills`; compatibility readers `.claude/skills` and `.agents/skills` are separately represented for each scope. All project readers carry ancestor-to-worktree descriptors. The resolver does not scan them. Native Linux/macOS/Windows lexical tests cover every shipped rule; exact host versions and OS-specific discovery remain untested rather than inferred. No IDE/cloud/managed variant is enabled.

[Config, Precedence order; Custom directory](https://opencode.ai/docs/config/) confirms plural `skills/` subdirectories and describes `OPENCODE_CONFIG_DIR` as an additional configuration source. It does not explicitly establish a replacement preferred skills write root; its custom-directory list names agents, commands, modes and plugins. This adapter therefore retains the explicit skills table and flags custom-directory skill discovery as unverified. It does not reinterpret `OPENCODE_CONFIG_DIR`, `XDG_CONFIG_HOME`, or another host's `CLAUDE_CONFIG_DIR` as an OpenCode skills write override. The returned warnings disclose that discovery descriptors are not exhaustive for custom configurations. These limits need further primary documentation and review before advertising configuration-complete support.

The skills page's **Troubleshoot loading** asks for unique names but does not establish duplicate precedence or link semantics. Neither is guessed. **Validate names** requires 1–64 lowercase ASCII alphanumeric characters with single hyphen separators, matching the skill folder; **Follow length rules** requires a 1–1024-character description. No additional reserved local name is documented. The forthcoming validator must apply these host constraints separately from the general specification. The installer's strict descendant-link rejection applies regardless of host discovery behavior.

`core_targets::opencode_native_writes_and_compatible_readers` tests every project/user native and compatibility rule and their physical overlap with default Claude/Codex placements without replacing native writes. `core_targets::opencode_context_and_configuration_limits` covers missing roots, unsupported variants, override non-inference and the returned configuration-gap warning. Neither test invokes a host, writes a skill store, verifies effective permissions, or claims discovery. All real-host discovery lists remain empty.
