# Permanent-removal API development

Status: experimental library planning/approval and Unix application for #113. The native Unix layer is under review and requires final-revision Linux/macOS evidence. Windows application and CLI deletion are not enabled by this layer; both remain mandatory before alpha. Do not publish the alpha before every [ADR 0009](adr/0009-permanent-removal.md) gate passes.

`removal::plan_removal` consumes a successful `SkillListing`, a zero-based location index, exact native skill basename, explicit `InstallContext` and `RemovalLimits`. It requires a complete present non-alias root/valid skill, rechecks the retained container and re-inspects the selected payload through the shared native no-follow inventory. Full root/entry stamps and original metadata bytes must still match discovery. A catalog/context resolution must identify that physical source container, so a mismatched context cannot silently change the preview.

`RemovalPlan` has private immutable fields and getters for canonical source target/scope, exact native path/name, selected root stamp, all descendant entries, original metadata bytes, total regular-file bytes, known readers and unresolved reader diagnostics. The selected root is an intended removal in addition to every returned descendant. Existing/unmanaged valid skills can be explicitly selected; no installed-by-this-program ownership is inferred. Unsafe/invalid metadata and incomplete listings are refused rather than gaining deletion authority.

Reader impact resolves every catalog target's declared scopes using only the supplied context and observes native/compatibility containers through the same explicit-anchor namespace walker. Matches use full physical container identity; native/read roles and unexpanded ancestor traversal are distinguished. Missing containers cannot currently alias the source. Unsupported/unverified/configuration-required targets, missing context, unsafe/unreadable locations and unexpanded ancestor uncertainty remain explicit unresolved evidence. This is catalog-known placement impact, not exhaustive host visibility or actual loading. Reader snapshots are observations, not atomic multi-root state.

Defaults/ceilings are 256/1024 catalog targets and 1024/4096 resolved location observations, plus the existing complete inventory limits. Fingerprint encoding streams into BLAKE3 with an 8 MiB ceiling and fails explicitly on excess. It includes an operation/version domain, catalog content, exact lossless native paths, root/container and descendant stamps, file digests, original metadata bytes, source target/scope/bytes and reader/unknown evidence. It is deterministic for unchanged observations with the same version/catalog/context, and intentionally invalidated by changed preconditions. It is not a secret, malware review, persistent identifier or ownership credential; representation changes between builds/versions are allowed.

`approve_permanent_removal` consumes the complete plan and requires its exact `confirmation_token`. This is an explicit library call to be made only after the caller presents every intended entry/known reader, warns that deletion is permanent with no undo, and requires stopped skill writers and controlled roots/ancestors. A generic copy approval or serialized receipt does not construct an `ApprovedRemoval`; neither type is deserializable. Approval itself writes nothing. Its wrapper exposes the exact preview for later native application, which must independently revalidate and accurately report all partial state.

The consumed listing's selected payload handles are released rather than retained inside the plan. Only the container namespace is retained. Independent clones/other readers can still prevent Windows DELETE access; future apply must report actual sharing refusal without force-closing handles or weakening no-follow semantics. `namespace_is_current` checks container bindings only and never claims to freeze payload contents. Planning/approval performs no staging, locks, chmod, environment reads, network access or execution of skill contents.

Reproduction: `cargo test -p agent-skills-kit --test removal_plan --locked`. Owned inert native fixtures cover core targets and user/project scopes; every payload entry/root and shared-reader roles; deterministic fingerprints and changed contents; wrong confirmations; stale/invalid/missing/wrong-context selections; target/location limits; no stage creation, deletion or changed source bytes. Linux/macOS/Windows CI is required for the final revision. Those are planning tests only; the separately implemented native behavior below has its own tests and evidence gate. Operation-specific CLI confirmation and Windows application remain required follow-up work.

## Native Unix application (review required)

`apply_removal(ApprovedRemoval)` consumes the explicit approval and returns a `RemovalReport`, including failures and partial progress. The common read-only preflight re-observes protected context roots, catalog-known reader/unknown evidence, retained container binding and complete source inventory; a changed observation fails without staging. The native backend repeats this before writes, uses only explicit retained descriptors, and never reads HOME, executes payloads, changes global environment or uses a path-based recursive delete.

On eligible Linux/macOS filesystems, exclusively create a private 0700 enclosure under the selected retained container with the existing no-ACL/ownership policy and a 100-name collision budget. Do not chmod an existing object or grant broader payload permissions. Move the selected immediate name to the enclosure's `payload` using the existing native `NOREPLACE`/`RENAME_EXCL` primitive. Unix cannot condition this name-based move on the previously observed inode. Therefore verify the actual detached identity and full inventory before any unlink, allowing only the root change-time difference expected from rename. A wrong/unsafe/stale detached object is never unlinked; attempt no-replace restoration of that exact captured object, preserving any concurrent original-name occupant. A failed detach does not give an unrelated pre-existing private `payload` restoration/cleanup authority.

After verification, retain a complete no-follow directory graph. Recheck current parent/entry bindings, directory stamps and each file's exact stamp/length/digest immediately before deepest-first unlink. Files/directories not in the preview are never added to the operation. Empty-directory removal refuses remaining contents. Update only the direct parent's expected metadata after this operation's own unlink; do not broaden permissions. The selected root is removed last, followed by the verified empty enclosure. Private-stage/source namespace loss stops cleanup rather than removing a substituted object. Source-parent ACLs or ownership-ignoring mounts are explicit unsupported creation policies, and real native permission failures are returned without repair.

The caller must control roots/container/ancestors and stop writers to the selected skill. Retained FDs/mappings and hostile same-identity staging mutation/reparenting remain outside the snapshot/containment guarantee; metadata checks plus unlink are not atomically identity-conditioned operations. Observable changes at the tested boundaries fail safely. No active-writer snapshot, global transaction, secure erasure, undo, power-loss durability or prefix-based orphan recovery is promised. Existing final-root symlinks remain refused; caller-controlled ancestor aliases follow the existing native root trust decision, not a new descendant-link exception.

`RemovalReport` preserves the original diagnostic labels and every intended descendant/root outcome: `Removed` confirms this operation's native namespace removal; `Remaining` means the same approved object's binding was observed after failure, without claiming unchanged bytes; `Unknown` cannot establish current identity/presence; `NotAttempted` makes no presence claim. Earlier removals remain reported after later failure. Original labels might now be occupied by another process's unrelated objects; never treat the report as permission to delete those names. `restored_before_removal` describes the captured detached object, which can be a refused replacement, rather than guaranteeing the original selected object was restored.

A retained enclosure has a diagnostic `retained_stage` label and separate `stage_location_uncertain`; when uncertain the label may name an unrelated replacement and must never be used as automatic cleanup authority. Unconfirmed creation, restoration failure, partial removal and cleanup failure remain explicit. `is_successful` requires all approved entries/root removed, no failure/cleanup findings and no retained or uncertain stage. Once any unlink succeeds there is no attempt to restore an incomplete tree as the original skill. A killed process cannot return a report and may leave an empty enclosure, complete detached payload or partial payload. Only the original fixture owner removes its entire test root during teardown; production has no prefix-driven recovery.

Bounds: complete source/reader preflights and detached verification use the recorded `RemovalLimits`; each approved file is additionally reread at most once for its pre-unlink digest, bounded by its approved length plus one excess-detection byte. The retained directory graph/entry order are bounded by the inventory count/depth ceilings. Per-inventory byte limits are per complete pass, not a total-byte promise across the finite preflight/verification passes. No new dependencies or unsafe FFI are introduced; the existing Unix ACL reader is shared with installation without changing its behavior.

Reproduce Unix application tests with `cargo test -p agent-skills-kit --lib removal:: --locked`. Owned original fixtures exercise actual complete removal, stale preflight without staging, source-directory/link substitutions in the final Unix name gap, edited detached content restoration, concurrent original-name occupants, unrelated private payload refusal, pre-unlink unknown entries, actual parent/child permission denial without chmod, accurate post-unlink partial failure, lost stage binding, explicit trusted ancestor aliases, new hardlinks and replaced container links. Two verified native removers use a bounded deterministic detach barrier: at most one removes the root and neither deletes the other's staging. Real child processes are killed before detach, after detach and after the first unlink; assertions check exact original/full/partial state and outside sentinels. The child helper is inert unless invoked by its explicit owned-fixture parent. Native Linux/macOS CI is still required for the final revision; Windows refusal in this intermediate layer is not successful Windows-removal evidence and cannot satisfy #113 or authorize alpha.

### Protected-root exclusion

Before approval, native physical ancestry checks reject a payload that equals or contains any explicitly supplied home/project/application-workspace root or successfully resolved host write/reader container. Missing configured roots are checked from their closest retained existing prefix, so a future root inside the payload is also protected. Caller-controlled ancestor aliases use native object identities, not string prefixes. An unavailable/ambiguous explicit context root fails planning rather than silently losing this protection. Each ancestry walk has a 128-directory ceiling and fails closed on cycles, errors or excess; it reuses the existing native planner parent/identity primitives. Unresolved/unverified host rules still remain explicit unknown evidence, not invented protected paths. No implicit real HOME lookup occurs: callers must supply truthful context under the root-trust contract.

Owned regression fixtures reject an overridden source that is the explicitly selected user home, project/workspace roots equal to or nested inside a skill, existing/missing host containers within it, and physical context-root aliases on Unix. The custom container metadata is an original synthetic safety fixture, not a new adapter or official host evidence. These checks perform no writes and do not turn a context/override value into removal authority.

Documented ancestor-reader uncertainty is preserved even when its exact root is missing or cannot be opened; a missing exact directory does not prove the host cannot discover an ancestor's skills. Such rules remain explicit unknown reader evidence and do not become invented paths or actual-loading claims.
