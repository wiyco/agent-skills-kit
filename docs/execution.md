# Execution preconditions

The executor provides `verify_plan(plan, limits)`, a bounded read-only preflight for an immutable library `InstallPlan`, and `apply_plan(plan, options)` for an explicitly approved native copy. A successful report is not a reusable authorization token, lock, or promise that the next operation will succeed.

The caller must control selected roots and their ancestor namespace under [the threat model](threat-model.md). A plan with any conflict/unsupported request fails as inapplicable. The verifier first checks every selected destination binding/absence, rereads every approved source from its original root binding, rereads unchanged destinations through retained handles, and checks destination namespaces again. Root stamps, complete entry stamps/types/modes/digests and original manifest bytes must still match. Byte-identical replacement entries with different identities are stale. A newly created destination is not silently adopted, even if it might otherwise be a valid skill.

`VerificationReport` returns successful source/destination counts and actual reread bytes/entry counts. Failures are typed and carry relevant native path labels without converting identity to lossy strings. No partial verification success authorizes writes. The library does not prompt, exit, change environment/CWD, execute content, or persist receipts. CLI rendering and machine encoding of these records belong to later work.

`VerificationLimits` defaults to the inventory reader's per-payload limits, 256 MiB total reread bytes and 16384 total payload entries. The total ceilings are 1 GiB and 65536 entries. Each reread receives the tighter remaining allowance; reader depth, path, regular-file and metadata bounds also apply. Callers with an explicitly larger validated plan can supply larger per-inventory bounds within the existing hard ceilings. Invalid settings and exhausted limits fail closed. A failing reader may probe one byte beyond its limit to detect growth; no subsequent payload is read after that failure.

Native integration cases compare complete before/after trees for eligible create/unchanged plans, mutated/replaced sources, newly appearing destination files/directories/links, substituted destination parents, changed unchanged-payload bytes/identity/modes/entry sets, exact budgets and already conflicting plans. All data is inert and roots are owned temporary fixtures. Existing reader tests cover deterministic lookup/open and read mutation points; this preflight layer does not claim copy/commit race coverage.

Linux/macOS use the same reviewed native inventory and namespace primitives as the planner; no dependency or host path is added. Windows uses the shared planner and verifier with the retained-handle NTFS backend described below. Privileged attacks, hostile staging/reparenting, mutable mounts/filesystems, universal collation behavior, arbitrary snapshot consistency and power-loss durability remain outside the accepted contract. Native operation-specific checks and exclusive commit are described below; unsupported backends never fall back to ordinary rename.


## Linux/macOS native copy and batch outcomes

Calling `apply_plan` approves exactly the immutable plan; there is no force option. Full preflight must pass before destination writes. The copy-byte ceiling defaults to 256 MiB and cannot exceed 1 GiB across all destinations, in addition to finite verification/reader limits. Each destination revalidates its source and relevant namespace. The batch creates missing parents exclusively with mode 0700 and reuses only parents created and still identity-bound by that same operation. An already-present component makes exclusive mkdir fail rather than authorize adoption. The subsequent no-follow lookup/open verifies its current binding and private permissions; mkdir/open is not an atomic creator-identity primitive. No reopened directory is chmodded to make setup succeed, and a restrictive owner-bit umask can produce an explicit failure/remnant. Caller namespace control and private-staging prerequisites remain necessary.

A private exclusively named 0700 staging directory is created under the retained destination parent. Resource directories/files are created with 0700/0600 initial modes; sources are opened one component at a time from retained source directories with no-follow/nonblocking flags. Exact opened stamps and bindings must match the approved inventory. Reads are bounded by approved file lengths plus one growth probe; staged bytes are read back and hashed before final restrictive modes. Every selected file and empty directory is included. Source ownership, ACLs, attributes, hard-link relationships and privilege bits are not copied. Final modes are source ordinary bits capped at 0755; directories become restrictive only after children are complete.

The source is completely revalidated after staging, completed stage/entry stamps and destination/owned parent bindings are checked again, and commit uses `rustix::fs::renameat_with(..., RenameFlags::NOREPLACE)`: Linux renameat2/RENAME_NOREPLACE or Apple renameatx_np/RENAME_EXCL. Native missing capability/filesystem support is an explicit error. There is no ordinary rename, delete, recursive merge or copy-into-existing fallback. Atomic visibility concerns the renamed destination root and is not power-loss durability. Staging is private by permissions, not hidden from same-identity processes; no real-host discovery test establishes that a host ignores staging names or recursive scans. Caller-controlled staging and the accepted same-identity threat limits still apply. No receipt is persisted.

`InstallReport` includes every physical destination and all copied source/target attribution, with Created, Unchanged, Failed or NotAttempted. Default stop-on-failure leaves later operations NotAttempted; callers can explicitly continue independent operations. Earlier successes remain installed. A whole-plan preflight failure leaves every outcome NotAttempted and reports its typed cause. Cleanup errors are separate: a successful commit followed by cleanup failure remains Created, with an unsuccessful overall report and a recovery diagnostic. I/O operation/kind/native code and validation failures remain structured.

The [receipt API](receipts.md) constructs bounded, versioned observational records from a borrowed plan/report with lossless native paths. It does not add persistence or confer cleanup authority; conversion failure leaves the full install report available.

## Cleanup authority and recovery

Staging cleanup is limited to recorded created objects within operation-private staging. Revalidate held identities and bindings before deletion, refuse a replaced stage or payload binding, restore owner cleanup access only to proven-owned staged directories, and remove only recorded files/directories in reverse order. Never recursively enumerate/delete unknown contents. Unknown extra entries or failed access checks leave a diagnostic. Failed creation setup can also leave an unconfirmed empty directory; report its path and never delete an object whose identity was not established. A recognizable staging prefix is not ownership proof. Operation-private staging excludes hostile same-identity mutation under the accepted contract; identity-check followed by unlink is not advertised as an atomic conditional deletion primitive against such an attacker.

Unused newly created destination parents are deliberately **retained** with `CreatedParentRetained` diagnostics. Outside private staging, identity-check followed by unlink cannot atomically condition deletion on the checked inode. Parents required by committed destinations stay without an error. Caller-owned existing parents are never chmodded or removed. Later recovery can inspect reported remnants; automatic deletion from a pathname/prefix is not authorized. A process kill may leave private staging or a complete install without a receipt. Injected Interrupted errors test orderly error handling, not an actual power-loss/process-kill guarantee.

## Permission and native source review (2026-10-16)

Mode bits alone do not prove private staging on ACL-inheriting filesystems. Creation parents and new stage/output objects with ACLs are refused conservatively. Newly created parents and the staging wrapper must remain mode 0700 with no ACL before reuse, commit or cleanup; a broken private context leaves recovery diagnostics. macOS MNT_IGNORE_OWNERSHIP volumes are rejected by their native mount flag instead of treating reported mode bits as effective access enforcement. An actual ownership-ignoring volume has not been mounted/tested; this conservative rejection follows the installed SDK mount contract. Linux checks descriptor-relative `system.posix_acl_access` and `system.posix_acl_default` through the existing rustix xattr wrappers; absent attributes/unsupported ACL storage are distinct from other read errors, and oversized ACL data is rejected without parsing. macOS uses a narrow owned-memory FFI wrapper around SDK `acl_get_fd_np` (ACL_TYPE_EXTENDED) and `acl_free`; any returned ACL, including an explicit empty ACL, is rejected. NULL/ENOENT from a live descriptor means the ACL property is absent; other errors fail. No ACL is changed or copied. This can refuse otherwise harmless ACL-bearing roots and is an explicit unsupported permission policy, not a suggestion to change a real user's permissions.

Reviewed primary references: [Linux rename manual](https://man7.org/linux/man-pages/man2/rename.2.html) (exclusive flags, filesystem support, errors), [Apple rename documentation](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/man/man2/rename.2), [Apple ACL retrieval/free contracts](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/acl_get_fd.3.html), [Apple inheritance description](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemDetails/FileSystemDetails.html), and local SDK `<sys/acl.h>`/manpages. The archived ACL retrieval page describes the generic interface imperfectly: exact Apple [acl_file.c at 71bbe350](https://github.com/apple-oss-distributions/Libc/blob/71bbe350ab79eef58113991d817ccc6165061a64/posix1e/acl_file.c) retrieves FILESEC_ACL from fstatx_np, explaining native absent-property behavior; this is code/API review, not new host-path evidence. macOS native tests exercise both absent ACL and an actual inherited-grant fixture. No upstream implementation is copied into the project.

The existing reviewed rustix 1.1.5 wrapper maps Apple NOREPLACE to RENAME_EXCL and returns NOSYS if that nonempty flag cannot be implemented; its ordinary-rename fallback is unreachable for this call. Exact Linux/Apple wrapper sources were inspected. libc 0.2.190 supplies existing native constants; there are no added dependencies or new tool installations. Backend eligibility remains the inventory reader's local Linux candidates and local APFS; actual no-replace execution still decides capability. Native CI records actual runner filesystem type in the commit-race test. A candidate filesystem is not a claim that every such deployment passed tests.

Native tests cover exact copies/reruns, multi-source/core-target batches, no writes on failed preflight, ACL refusal, actual exclusive commits against newly appearing files/empty directories/links, two synchronized installers, source mutation points, injected copy/permission/capability/interruption failures, parent substitution, stage cleanup substitution, retained unused parents, post-commit cleanup failure and partial outcomes. Checkpoint injection is internal test scaffolding, not a public callback that can bypass checks. Injected ENOSYS is an error at the pre-commit checkpoint, not proof that an unavailable native syscall was exercised; actual unsupported-kernel behavior remains a deployment limitation and the no-fallback path is source-reviewed. Direct native filesystem behavior and simulated failures are reported separately. The current copier retains file/directory handles through verification/cleanup; large entry counts can hit process descriptor limits and fail with native I/O diagnostics. Actual process-kill coverage is documented in the ASK-012 evidence matrix. Device/quota/mount behavior, all candidate filesystems and real-host discovery remain unvalidated.

## Windows read-only verification

Eligible Windows NTFS plans use the same bounded verification implementation as Linux/macOS. It rereads complete source snapshots and retained unchanged payloads, compares native identities/bytes/attributes, rechecks selected namespace security preconditions before and after inspection, and rejects stale or inapplicable plans. There is no Windows-specific duplicate verification policy.

Reproduce with `cargo test -p agent-skills-kit --test execution_preflight --locked -- --nocapture` on Windows. Owned fixtures exercise successful read-only create/unchanged verification, exact/insufficient/invalid budgets, preserved manual edits, identical-byte replacements with different identities, read-only intent changes (original permissions restored), extra entries, actual file/directory reparse points and competing destination entries. Missing reparse privileges fail explicitly. `windows_public_apply_copies_then_reports_unchanged_and_preserves_conflicts` exercises the public facade: original bytes/attributes, create, fresh unchanged, and refused conflict with preserved manual edits.

## Windows native copying

`apply_plan` dispatches eligible Windows plans to the library's retained-handle backend. The same whole-plan preflight and copy budget apply. Only fixed local NTFS roots with no reparse ancestors are eligible. Native evidence is Windows Server 2025 x64/NTFS; other architectures, desktop versions and filesystem/security configurations are unvalidated.

Missing parents and stages are created exclusively with protected user-only ACLs. Payload files/directories also start protected, so bypass-traverse privileges cannot expose them through the wrapper. Newly created destination parents remain private by policy. Existing parents are never changed. Files are copied using approved source identities and bounded original bytes, hashed/read back, and ordinary DOS read-only intent is applied. Full stage entry sets, identities/security and original digests are checked again before commit; metadata alone is insufficient to detect same-length staged changes.

All descendant copy handles close before `NtSetInformationFile(FileRenameInformation)` renames the held root relative to the held parent with replacement disabled. No path-based move fallback exists. After commit, all known permission handles are reacquired while the tree is private, full identities/security are checked and handles retained through per-object parent-before-child destination inheritance via `CreatePrivateObjectSecurityEx` and `NtSetSecurityObject`. Source ACLs, ownership, streams, extended attributes and privilege-bearing metadata are never copied. This ordinary destination-inheritance policy does not snapshot SACL/audit/integrity configuration or emulate every enterprise security policy.

A finalization failure explicitly reports committed content with failed/partial permissions and honors batch stop policy. It never authorizes rollback. Cleanup verifies all recorded object identities/security before mutation, then removes only held owned objects in reverse order; read-only cleanup changes only owned attributes. Unknown extra entries stop cleanup and retain diagnostics. Unused created parents remain reported. Retry never adopts orphan ownership or implicitly repairs permissions on an unchanged tree.

See [native backend review](verification/windows-backend.md) and [ASK-012 evidence](verification/ask-012.md) for exact successful revisions, tests and failure history. Process-kill tests cover three boundaries, not power-loss durability or every instruction. Handle retention can hit process limits and fail with structured I/O diagnostics. Host discovery, second-user/enterprise ACL behavior and network filesystems are unvalidated.

## Committed payloads with permission failures

`OutcomeStatus::CommittedWithPermissionFailure(error)` distinguishes a complete no-replace payload commit followed by failed or partially completed destination permission finalization. It is not an ordinary success or a pre-commit failure. `InstallReport::is_successful()` returns false; `OutcomeStatus::payload_was_committed()` returns true for this result and `Created`, and false for unchanged/not-attempted/pre-commit-failed operations. Earlier successful destinations remain installed, and the committed payload is never rolled back or reclaimed as staging. Windows applies stop-on-failure to this result and preserves its typed cause.

Schema-1 receipts retain their existing fields/status/failure codes for compatibility. Projection records `Failed`, the coarse native cause/path/OS code, and the explicit operation label `payload committed; destination permission finalization failed`. The live report retains the original typed error and operation. Projection rejects this result for an unchanged/conflicting/unsupported preview. No receipt, status or diagnostic creates deletion authority. A failed receipt must not be interpreted as proof that the destination is absent.

`committed_permission_failures_are_explicit_unsuccessful_and_receipt_compatible` tests these distinctions, compatible JSON round trips and invalid unchanged-plan projection on all three native platforms with an explicitly synthetic report. It performs no installation; native commit/finalization and interruption tests are separate evidence in the Windows backend review.
