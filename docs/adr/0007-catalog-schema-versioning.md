# ADR 0007: Explicit offline catalog schema version 1

Status: implemented schema proposal in ASK-004; bundled evidence examples follow in a dependent PR.

Use a JSON document with an explicit integer `schema_version` and typed target, variant, scope, platform, path-base, discovery, status, and evidence records. Version 1 is accepted exactly; other versions, unknown enum values/fields, duplicate IDs/aliases/variants, unsafe path components, inconsistent scope bases, and malformed provenance are rejected. Parsing is bounded to 2 MiB. No network, filesystem, or process-environment access occurs.

IDs and aliases share one case-sensitive namespace. A product/variant pair is unique, and an ID must never be reassigned to another product or variant. Renames retain the old ID as an explicit alias only when meaning stays identical. A CLI, IDE, cloud, or application-workspace variant is a separate definition; ancestry or branding does not establish shared paths. Breaking wire interpretation requires a new schema version and explicit migration, not silently reinterpreting existing records. Public enums are non-exhaustive for additive Rust API evolution; structural/wire changes remain reviewable compatibility decisions.

Preferred writes and readable discovery locations are separate fields. `None` means no known write path, never an inferred default. Bases are explicit caller home/project/application-workspace context or an exact environment-variable name with a separately represented optional fallback. Components are literal, not templates or shell expressions. A future resolver must reject missing context, unsupported combinations, and unverified rules before producing an advertised installable destination.

Documentation review state/source, resolver tests, and real-host discovery tests are separate evidence dimensions. A syntactically valid HTTPS URL is not proof of host ownership or content review. Bundled records need current manual primary-source review, including redirect resolution and version/platform limitations. Schema tests use original synthetic metadata at `example.invalid` and are not host path evidence. No field or constructor asserts that copying or discovery has been tested merely because metadata parsed.

Validated iteration and exported documents sort IDs, aliases, scopes, and platform sets deterministically. Discovery order stays explicit because it may communicate host precedence. Catalog construction validates without mutating the caller's environment; records are immutable through the validated registry. The catalog is bundled/versioned, not refreshed over the network during installation.

## Dependency review (2026-10-16)

Use Serde for typed JSON serialization/deserialization and serde_json for a bounded JSON parser with location-aware errors. Handwritten JSON parsing would add unnecessary parser/security complexity. [serde 1.0.229](https://crates.io/api/v1/crates/serde/1.0.229) and [serde_json 1.0.154](https://crates.io/api/v1/crates/serde_json/1.0.154) were current non-yanked stable releases in the primary registry. Their primary repositories are [serde-rs/serde](https://github.com/serde-rs/serde) and [serde-rs/json](https://github.com/serde-rs/json); registry update dates were 2026-07-18 and 2026-10-11. Both declare `MIT OR Apache-2.0`; declared MSRVs are 1.56 and 1.71, below this workspace's measured 1.85.0. Exact versions/checksums are in Cargo.lock; CI must verify the actual graph on the declared MSRV.

Reviewed locked transitive metadata: serde_core/derive, proc-macro2, quote, syn, and itoa declare `MIT OR Apache-2.0`; memchr declares `Unlicense OR MIT`; zmij declares MIT; unicode-ident declares `(MIT OR Apache-2.0) AND Unicode-3.0`. Maximum declared transitive MSRV is 1.71. These implement derives, JSON string scanning, number encoding and Unicode identifiers; none adds installer networking or an async runtime. This is not a substitute for ASK-023's advisory/license automation. Sources/code from compared installers are not reused. Local downloads/builds use a task-local Cargo cache rather than changing the developer's global setup.
