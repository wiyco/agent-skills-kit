# ASK-008: Define the filesystem threat model and copy safety contract

## Goal

Agree on the guarantees and limits before writing an installation engine.

## Context

Read `AGENTS.md`, `docs/architecture.md`, and `docs/testing.md` before implementation. This is a WIP, not-ready-for-use English-language OSS source preview, not a supported or published library/CLI. Source visibility is separate from crate and binary publication; see `docs/public-readiness.md` and `docs/release.md`.

## Scope

- Document trust boundaries for source content, caller-supplied roots, existing destination trees, environment variables, and concurrent filesystem changes.
- Specify no-clobber defaults, source/destination overlap rejection, symlink/reparse-point policy, race handling, permission policy, and staging cleanup ownership.
- Distinguish same-filesystem commit behavior from cross-target partial completion; do not promise a global transaction.
- Select a defensible OS/backend strategy for no-follow operations and atomic no-replace behavior, or explicitly reject unsupported conditions.
- State that format validation and safe copying do not establish that a skill is benign to execute.

## Acceptance criteria

- [ ] The threat model includes traversal, symlink escape, TOCTOU, hard links, reparse points, device/FIFO files, source mutation, permission errors, and process interruption.
- [ ] An exists-check followed by ordinary rename is not accepted as a race-free no-clobber guarantee.
- [ ] Trusted root canonicalization and descendant no-follow checks are specified separately.
- [ ] Untrusted skill instructions never become instructions for the installer or implementation agent.
- [ ] Maintainer review records the guarantees supported for v0.1 and any unsupported adversarial cases.

## Verification

- Write attack/failure scenarios that ASK-012 can turn into regression tests.
- Review library choices against official API/platform behavior at implementation time.
- Record a safety ADR before ASK-010 begins.
